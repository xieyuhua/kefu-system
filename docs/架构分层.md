# 后端分层架构

> 组织方式：**按三端划分业务模块 → 端内再按技术分层**；三端共用 `core` 内核，内核之下是 `platform` 基础设施，最底层 `pkg` 通用能力。
> 一个端内改动只进一个端目录；跨端能力进 core；core 不得反向依赖端。

## 总体结构

```
server/
  main.go                     启动装配：config → db → cache → seed → route
  pkg/                        通用层：可复用、无业务耦合
  internal/
    route/router.go           路由汇总（唯一的路由真值来源，77 条）
    core/                     共享业务内核（service + repository，少量跨端 handler）
    modules/                  三端：client / agent / admin（handler + service）
    platform/                 基础设施（被 core 与各端依赖，自己不依赖它们）
```

## 分层与依赖

```
modules/{client,agent,admin}   端：HTTP 入口与端内编排
        │
        ▼
      core/*                   共享业务内核：会话、消息、客户、渠道、账号、自动回复
        │
        ▼
      platform/*               基础设施：WS、通知、鉴权、配置、种子、附件
        │
        ▼
      pkg/*                    通用能力：响应壳、存储、缓存、gin 辅助
```

**硬规则**
- 端之间**不得互相 import**（三端平行，互不引用）。
- `core` **不得** import `modules`。
- `platform` 不得 import `core` / `modules`。
- `pkg` 不得 import `internal/...`。

## pkg —— 通用层

| 包 | 职责 |
|---|---|
| `pkg/response` | 统一响应壳 `{code, message, data}` |
| `pkg/storage` | GORM 连接、事务、分页 |
| `pkg/cache` | 缓存抽象（Redis / 内存降级），配置由 `Init(Options)` 注入 |
| `pkg/httpx` | 通用 gin 辅助：参数解析、JSON 绑定 |
| `pkg/util` | 时间格式化等工具 |

## platform —— 基础设施

| 包 | 职责 |
|---|---|
| `model` / `dto` | 数据实体；出入参与视图对象 |
| `authctx` | gin 上下文登录态：`CurrentUser` / `IsAdmin` / `UserID` / `TenantID` |
| `auth` / `middleware` | 密码与 token、JWT 中间件 |
| `realtime` | WebSocket Hub、事件发布、站内通知、厂商推送 |
| `setting` | 租户级配置（默认图片、提示音） |
| `card` | 订单/商品卡片 JSON 构造 |
| `idgen` | 渠道 `app_id` 生成与唯一性校验 |
| `ipinfo` | IP 归属地解析 |
| `config` / `db` / `seed` | 应用配置、GORM 连接、演示数据 |

platform 需要业务能力时用**回调注入**，不反向 import：

```go
// 各 core 包在自己的 init 里注入，platform 只认函数值
conversation: realtime.SetAgentOfflineHook(NewService().ReleaseAgentConversations)
account:      authctx.SetUserLoader(NewService().LoadUser)
notify:       realtime.SetDeviceLister(NewService().ListDevicesForPush)
```

这样平台层不必复制业务 SQL（例如推送前的设备查询只有 `core/notify` 一份实现），
代价是回调未注册时需静默降级，注册点必须集中在各 core 包的 `init.go`，便于排查。

## core —— 共享业务内核

| 包 | 职责 | 依赖 |
|---|---|---|
| `core/account` | 账号、登录、个人资料、子账号数据 | — |
| `core/channel` | 渠道、渠道类型、二维码、接入链接解析 | — |
| `core/customer` | 客户、标签、订单、商品 | — |
| `core/conversation` | 会话、消息、归档、WebSocket、离线同步查询 | account、channel、customer |
| `core/automation` | 自动回复规则、转人工判定 | conversation |
| `core/notify` | 站内通知、设备注册与推送目标查询 | — |
| `core/upload` | 文件上传（游客端与客服端共用） | customer |

**跨端 handler 允许留在 core**（只有一条路由、却被多个端调用），需在文件头注明「跨端端点」：

- `core/account`：登录、登出、当前用户、改资料、改密码 —— 客服端与后台端各有登录页。
- `core/customer`：订单与商品列表 —— 后台管理页与客服端选择器共用同一个接口。
- `core/upload`：上传 —— `/api/upload` 与 `/api/guest/upload` 共用实现。

## modules —— 三端

| 端 | 入口 | 负责 | 典型端点 |
|---|---|---|---|
| `modules/client` | `kefu.html` · `/kefu/` | 用户端免登录接入 | `guest/init`、`guest/message`、`guest/messages`、`/ws/guest` |
| `modules/agent` | `chat.html` · `/chat/` | 客服工作台 | 会话接管/转接/结束/归档、发消息、客户资料、标签、离线补拉、设备注册、演示面板、`/ws` |
| `modules/admin` | `admin.html` · `/admin/` | 管理后台 | 渠道与渠道类型、子账号、客户与标签、订单商品管理、自动回复、设置、统计、对话记录、设备自检 |

端内只有两层（**按业务域拆成独立文件**，一个文件只放一个业务子域的声明）：

| 文件 | 职责 | 禁止 |
|---|---|---|
| `<域>_handler.go` | 解析参数 → 调 service/core → 写响应 | 直接访问数据库 |
| `<域>_service.go` | 端内编排、视图组装 | 拼接跨模块 SQL（必要时下沉 core） |
| `handler.go` | 仅 `Handler` 结构体 + `NewHandler()` | 放业务逻辑 |
| `service.go` | 仅 `Service` 结构体 + `NewService()` | 放业务逻辑 |

文件命名与拆分规则（`core/` 与 `modules/` 一致）：

- 文件名 = `<业务域>_<层>.go`，例如 `order_service.go`、`tag_repository.go`、`channel_handler.go`
- 一个文件只承载一个业务子域；同一子域的三层分布在三个文件里（`customer_service.go` / `customer_repository.go` / `customer_handler.go`）
- 结构体定义与构造函数单独放 `handler.go` / `service.go` / `repository.go`，其余文件只加方法
- 单文件建议 ≤300 行；超过就按子域再拆（当前生产代码最大 307 行）

端内共享的 `devices`、`notifications` 与概览统计 SQL 暂放在对应端 service 中（注释已说明）；若后续被多端复用，再下沉 `core`。

## 数据访问归属

- 每张表的写入只有一个归属：`core/*/<域>_repository.go` 或端内 service（如 `devices`、`notifications`）。
- `repository` 可以读任意表，但**只写本模块自己的表**。
- 少量跨表只读（如客户统计会话数）就地实现，文件头注明原因。

## 调用形态：结构体 + 方法（不用包级函数）

所有业务能力以**结构体方法**形式提供，包级只保留构造函数与纯工具函数。

```go
// core/conversation/repository.go
type Repository struct{}
func NewRepository() *Repository { return &Repository{} }
func (r *Repository) FindByID(tenantID, id uint) (*model.Conversation, error)

// core/conversation/service.go
type Service struct {
    repo     *Repository
    customer *customer.Service     // 跨域依赖，构造时建好
}
func NewService() *Service {
    return &Service{repo: NewRepository(), customer: customer.NewService()}
}
func (s *Service) List(tenantID, userID uint, isAdmin bool) ([]*dto.ConversationVO, error)

// modules/agent/service.go
type Service struct {
    conv *conversation.Service
    cust *customer.Service
}
func NewService() *Service

// modules/agent/handler.go
type Handler struct{ svc *Service }
func NewHandler() *Handler
func (h *Handler) ListConversationsHandler(c *gin.Context)
```

装配方式：**构造函数内自建依赖**（推荐），`route` 只负责 new 一次 handler：

```go
accH    := account.NewHandler()
clientH := client.NewHandler()
agentH  := agent.NewHandler()
adminH  := admin.NewHandler()
authed.GET("/conversations", agentH.ListConversationsHandler)
```

约定：
- 方法统一**指针接收者**：`(r *Repository)` / `(s *Service)` / `(h *Handler)`。
- 跨包调用走字段：`s.customer.FindByID(...)`、`s.conv.List(...)`，不再写 `customer.FindByID(...)`。
- 保留包级函数的只有：`NewXxx()` 构造函数、`init()` 钩子、以及无依赖的纯函数（`orDefault`、`matchKeywords`、`AccessPath`、`messagePreview`、`randomNickname` 等）。
- `platform/` 与 `pkg/` 保持既有形态（基础设施与通用能力，无状态或单例），不强制结构体化。

## 新增一个接口的标准动作

1. 判断属于哪一端（用户端 / 客服端 / 后台端）；三端都要用则进 `core`。
2. 数据访问：`core/<域>/<子域>_repository.go` 给 `*Repository` 加方法。
3. 业务：`core/<域>/<子域>_service.go` 给 `*Service` 加方法；端内编排写 `modules/<端>/<子域>_service.go`。
4. handler：`modules/<端>/<子域>_handler.go` 给 `*Handler` 加 `XxxHandler` 方法。
5. `route/router.go` 注册（`/xxx/:id` 之前先注册静态路径）。

## 命名规范

| 前缀 | 语义 | 返回 |
|---|---|---|
| `Find*` | 查单条，找不到返回错误 | `(*model.X, error)` |
| `List*` | 查多条 | `([]*model.X, error)` |
| `Count*` | 计数 | `(int64, error)` |
| `Create*` / `Insert*` | 新增 | `error` |
| `Save*` / `Update*` | 更新 | `error` |
| `Delete*` / `Remove*` | 删除 | `error` |

handler 统一带 `Handler` 后缀（`agent.ListConversationsHandler`），避免与同包 service 同名。

## 指针使用约定（全层强制）

所有分层一律使用结构体指针，避免整行拷贝：

```go
func FindUserByID(tenantID, id uint) (*model.User, error)      // 单条 → 指针
func ListUsersByTenant(tenantID uint) ([]*model.User, error)   // 列表 → 指针切片
func CreateChannel(c *model.Channel) error                     // 写入 → 收指针
func BuildOrderCard(o *model.Order) string                     // 只读辅助 → 收指针
```

- 值类型只用于纯标量参数（id、字符串、分页）与 `dto` 视图对象。
- Go 1.22+ 循环变量按迭代独立，`for _, x := range list { out = append(out, &x) }` 无指针别名问题（本项目 go 1.26）。

## GORM 收敛现状

| 位置 | 用途 |
|---|---|
| `core/*/<子域>_repository.go`、部分端内 service | 业务数据访问 |
| `pkg/storage`、`platform/db` | 连接与事务 |
| `platform/{realtime/store.go, ipinfo, idgen, setting}` | 基础设施少量直写（文件头注明例外） |
| `main.go` | `storage.SetDB(db.DB)` 注入一次 |
| `platform/seed` | 启动时一次性演示数据引导 |

`handler` 与 `service`（端内编排）两层不含 GORM 链式调用。
