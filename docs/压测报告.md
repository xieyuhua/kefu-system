# 压测报告与压测方法

> 记录客服系统的压测方法、历次实测数据、瓶颈定位与优化效果。
> 压测脚本：`server/cmd/bench`（零依赖，仅标准库）。

---

## 一、压测脚本

### 1.1 位置与用法

```powershell
# 1) 启动服务（默认 8480）
cd server; go run .

# 2) 准备 20 个固定测试访客（脚本的发消息/初始化场景复用它们）
$CH = "kefu_e111203e"     # 换成实际渠道 app_id（后台「渠道管理」可见）
0..19 | ForEach-Object {
  Invoke-RestMethod "http://127.0.0.1:8480/api/guest/init?channel=$CH&uid=benchv_$_&nickname=BENCH$_"
}

# 3) 取管理员 token（读接口需要）
$TOKEN = (Invoke-RestMethod -Uri http://127.0.0.1:8480/api/auth/login -Method Post `
          -ContentType 'application/json' -Body '{"account":"admin","password":"admin123"}').data.token

# 4) 压测（每档并发 6 秒）
go run ./cmd/bench -token $TOKEN -ch $CH -d 6s
```

### 1.2 覆盖场景

| 场景 | 路径 | 说明 |
|---|---|---|
| 会话列表 | `GET /api/conversations` | 读路径，含可见范围过滤 + 批量预取 |
| 统计 | `GET /api/conversations/stats` | 读路径，侧边栏数字 |
| 关键词搜索 | `GET /api/conversations?keyword=` | 读路径，`LIKE` + 子查询 |
| 发消息 | `POST /api/guest/message` | 写路径，衡量往返次数与刷盘开销 |
| 访客初始化 | `GET /api/guest/init` | 写路径，含客户定位/创建 |

每档并发：**10 / 50**；输出 RPS、p50、p90、p99、错误数。

### 1.3 注意事项

- **热点会话**：发消息场景固定打 20 个会话，属于极端热点（MySQL 行锁排队）。真实流量分散时吞吐更高。
- **业务错误计入错误数**：接口 HTTP 恒 200，脚本读 `code` 字段判定成败，避免把失败算成成功。
- **数据量会影响结果**：会话表条数显著影响列表查询。报告中的数字都标注了当时的会话总数。

## 二、测试环境

| 项 | 配置 |
|---|---|
| 应用 | Windows 本机，Go 1.26，端口 8480 |
| 数据库 A | SQLite `data/kefu.db`（本机，后开 WAL） |
| 数据库 B | MySQL `192.168.2.6:3308`（**局域网远程**，约 1–3ms RTT） |
| 压测端 | 同机运行 `server/cmd/bench` |

> 关键背景：**应用与 MySQL 不同机**，每次查询都有网络往返。这放大了「查询次数」的代价，是本次优化的主线。

## 三、优化前的基线

### 3.1 SQLite（默认配置，无 WAL）

| 场景 | 并发 | RPS | p50 | p99 |
|---|---|---|---|---|
| 会话列表 | 10 | 167 | 59ms | 80ms |
| 会话列表 | 50 | 175 | 288ms | 365ms |
| 统计 | 10 | 2600 | 3.3ms | 18ms |
| 发消息 | 10 | **10** | 110ms | 6.9s |
| 访客初始化 | 10 | 28 | 38ms | 2.5s |

**结论**：读接口正常，写路径崩塌——发一条消息要跑 3 个独立事务（消息 / 会话摘要 / 客户活跃时间），每次一次刷盘。

### 3.2 MySQL（远程库，459 条会话）

| 场景 | 并发 | RPS | p50 |
|---|---|---|---|
| 会话列表 | 10 | 40 | 249ms |
| 会话列表 | 50 | 52 | 1068ms |
| 统计 | 10 | 328 | 26.5ms |
| 发消息 | 10 | 29 | 353ms |
| 访客初始化 | 10 | 60 | 159ms |

**根因定位**：抓 SQL 日志发现**一次会话列表请求发了 56 条 SELECT**（20 条会话 × 约 3 次）：
每条会话都单独查客户、订单数、标签、渠道、客服。SQLite 是本机调用（微秒级）还能扛，
MySQL 每次要走局域网，56 × 2ms ≈ 112ms，正好对上 p50 249ms。

## 四、优化措施与效果

### 4.1 优化清单

| 提交 | 内容 | 解决的问题 |
|---|---|---|
| `4091b04` | 消息附属写异步批量落库（`WriteBatcher`） | 发消息 3 次刷盘 → 1 次（消息本体同步、摘要/活跃时间异步攒批） |
| `cfc207d` | 会话列表消除 N+1（56 → 6 条 SQL）+ 客户互斥改一次性预取 | 列表/搜索的往返次数 |
| `8e08180` | 渠道、系统设置进程内 TTL 缓存；访客活跃时间异步落库 | 每条消息重复读配置 |
| `2e32b76` | 上行消息复用已查到的会话 | 去掉重复的会话查询 |
| `1d85475` | 渠道解析按 app_id 缓存；机器人关闭跳过规则查询 | 每次请求整表查渠道 + 白查规则 |

### 4.2 MySQL 优化后（321 条会话）

| 场景 | 并发 | RPS | p50 | p90 | p99 | 错误 |
|---|---|---|---|---|---|---|
| 会话列表 | 10 | 295 | 30ms | 39ms | 140ms | 0 |
| 会话列表 | 50 | **546** | 82ms | 137ms | 224ms | 0 |
| 统计 | 10 | 489 | 20ms | 23ms | 29ms | 0 |
| 统计 | 50 | 580 | 82ms | 125ms | 217ms | 0 |
| 关键词搜索 | 10 | 217 | 38ms | 67ms | 173ms | 0 |
| 关键词搜索 | 50 | **471** | 102ms | 149ms | 214ms | 0 |
| 发消息 | 10 | 34 | 274ms | 436ms | 500ms | 0 |
| 发消息 | 50 | 93 | 550ms | 732ms | 1329ms | 0 |
| 访客初始化 | 10 | 114 | 75ms | 130ms | 227ms | 0 |
| 访客初始化 | 50 | 229 | 216ms | 274ms | 338ms | 0 |

### 4.3 提升幅度

| 场景 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| 会话列表 c=50 | 52 RPS / 1068ms | **546 RPS / 82ms** | **10.5×** |
| 会话列表 c=10 | 40 RPS / 249ms | 295 RPS / 30ms | 7.4× |
| 关键词搜索 c=50 | 50 RPS / 1077ms | 471 RPS / 102ms | 9.4× |
| 访客初始化 c=10 | 60 RPS / 159ms | 114 RPS / 75ms | 1.9× |
| 访客初始化 c=50 | 84 RPS / 550ms | 229 RPS / 216ms | 2.7× |
| 发消息 c=10 | 29 RPS / 353ms | 34 RPS / 274ms | 1.2× |

> 优化后 MySQL 的列表性能（295 RPS / 30ms）已经优于本地 SQLite（167 RPS / 59ms）——
> 证明此前 MySQL 慢是 N+1 造成的，不是数据库本身。

### 4.4 SQLite + WAL 参考数据

给 SQLite 连接串加 `?_journal_mode=WAL&_busy_timeout=5000` 后（单机部署推荐）：

| 场景 | 并发 | RPS | p50 |
|---|---|---|---|
| 发消息 | 10 | 359 | 3.7ms |
| 发消息 | 50 | 410 | 3.7ms |
| 访客初始化 | 10 | 392 | 25ms |

无 WAL 时并发写会直接报 `database is locked`（实测约 50% 请求失败），**单机部署务必开 WAL**。

## 五、当前瓶颈与建议

### 5.1 剩余瓶颈

发消息单次仍约 220–270ms，其中绝大部分是 **4~6 次数据库往返 × 20–30ms 网络 RTT**，不是 MySQL 计算耗时。
每次发送的剩余往返：查客户 → 查会话（已复用）→ 插消息 → 查规则（机器人关闭可跳过）→ 附属写（异步）。

### 5.2 建议（按性价比排序）

1. **应用与 MySQL 同机/同机房部署** —— RTT 20ms → 0.1ms，写路径可再快一个数量级，**零代码改动**，是生产上线前最该做的一件事。
2. **客户 + 会话合并成 1 条 JOIN** —— 再省 1 次往返（未做）。
3. **读写分离** —— 列表/统计走从库。
4. **历史会话归档** —— 让主表保持小而热，列表查询更稳。
5. **列表短 TTL 缓存（2–5s）** —— 客服列表非强实时，可挡掉大部分重复请求。

### 5.3 已验证可用的缓存口径

| 数据 | TTL | 失效方式 |
|---|---|---|
| 渠道（按 ID / 按 app_id） | 5s | 到期自动 |
| 系统设置（tenant+key） | 5s | `SaveSetting` 主动失效 |

> 配置改动最多延迟 1 个 TTL 生效，对客服系统可接受。
